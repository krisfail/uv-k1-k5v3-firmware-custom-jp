# フォント／ビットマップの割り当て台帳

この文書は，表示文字を追加する前に，既存のフォントとビットマップの割り当てを確認するための台帳です．ここで扱うコードはファームウェア内部の1バイト文字コードであり，Unicodeそのものではありません．

開発者向けの台帳であり，利用者向けの表示案内ではありません．利用者向けの説明は[README.ja.md](../README.ja.md)，AIエージェント向けの規則は[AGENTS.md](../AGENTS.md)を参照してください．

## 既存の文字コード

以下を，K5／K1で共有する表示上の正規対応として扱います．これはUnicodeのコードポイントではなく，ファームウェア内の1 byteコードです．

| 範囲 | 用途 | 備考 |
| --- | --- | --- |
| `0x20` | 空白 | ASCII表示領域の空白 |
| `0x21`–`0x7E` | ASCII印字可能文字 | `gFontBig`の標準領域．現在の実装ではASCIIとして扱う |
| `0x7F` | 未使用／互換領域 | JIS X 0201の文字として扱わない |
| `0x80`–`0x97` | プロジェクト固有の日本語拡張 | JIS X 0201ではない．主にメニュー用漢字・かな |
| `0x98` | 日本語大グリフ「専」 | 公開フォントの線構造を手掛かりに独立再構成 |
| `0x99` | 日本語大グリフ「用」 | 公開フォントの線構造を手掛かりに独立再構成 |
| `0x9A`–`0xA0` | プロジェクト固有の予約領域 | JIS X 0201ではない．追加前に両機種のinventoryを確認する |
| `0xA1`–`0xDF` | JIS X 0201半角カタカナ | 下表の対応を正本とする |
| `0xE0`–`0xFF` | K1固有の拡張領域 | JIS X 0201ではない．長音や追加表示に使う場合は個別に注釈する |

### `0xA1`–`0xDF`の正規対応

| 範囲 | 文字 |
| --- | --- |
| `0xA1`–`0xAF` | `｡ ｢ ｣ ､ ･ ｦ ｧ ｨ ｩ ｪ ｫ ｬ ｭ ｮ ｯ` |
| `0xB0`–`0xBF` | `ｰ ｱ ｲ ｳ ｴ ｵ ｶ ｷ ｸ ｹ ｺ ｻ ｼ ｽ ｾ ｿ` |
| `0xC0`–`0xCF` | `ﾀ ﾁ ﾂ ﾃ ﾄ ﾅ ﾆ ﾇ ﾈ ﾉ ﾊ ﾋ ﾌ ﾍ ﾎ ﾏ` |
| `0xD0`–`0xDF` | `ﾐ ﾑ ﾒ ﾓ ﾔ ﾕ ﾖ ﾗ ﾘ ﾙ ﾚ ﾛ ﾜ ﾝ ﾞ ﾟ` |

`0x80`–`0xA0`と`0xE0`–`0xFF`をJIS X 0201として解釈してはいけません．また，JIS X 0201ローマ字集合とASCIIでは`0x5C`と`0x7E`の意味が異なるため，既存ファームウェアでは標準フォントの実装どおりASCIIとして扱います．

### 現行大字形の監査結果

rainy由来の基準配列では，`gFontBig`の実行時添字は`code - 0x21`です．このため，`0x9A`–`0xA5`と`0xB0`が空白になり，`0xA1`と注釈された行は実行時には`0xA6`に対応します．完全一致する重複も少なくとも`0xA6`と`0xDD`，`0xA7`と`0xB1`で確認されています．一方，small版には`0xA1`–`0xDF`の対応字形があります．

K1は`gFontBigJapanese`と`gFontSmallJapanese`を別配列で持つため，K5の連続配列をバイト列として移植してはいけません．atlasの「使用中／空き」は現行バイト列の状態であり，この節の文字表は再構成時の正規割り当てです．

特大字形は`gFontJapaneseExtraLarge`として分離しています．10列×2ページ（20 bytes）の形式で，起動画面専用の`0x80`（受），`0x81`（信），`0x98`（専），`0x99`（用）の4スロットだけを持ちます．通常大字形と異なり，16行すべてを字形領域として編集できます．表示場所に応じて`UI_PrintString`と`UI_PrintStringJapaneseExtraLarge`を使い分けます．

`0x80`–`0x97`の割り当ては次のとおりです．

`受 信 変 調 追 加 保 存 削 除 名 長 短 押 音 電 源 更 圧 表 示 画 面 無`

K1では大・小フォントの`0xE0`に長音「ー」を割り当てています．K5では長音を既存のASCIIハイフン（`0x2D`）で表示するため，機種共通の文字列を増やすときは，まず表示文字列側で分岐できるか検討します．

## 大字形の格納形式と表示範囲

通常大字形は欧文・日本語とも16行（7列×2 OLEDページ）の固定長データです．0–15行がST7565へ渡る実データであり，字形ごとの点灯範囲は一致しません．表示行2–11は既存フォントの配置を確認するための参考範囲にすぎず，0–1行と12–15行を空白に固定する規則ではありません．

特大字形は起動画面専用の10列×2ページです．K1の4字は16行すべてを使用可能で，通常大字形の参考範囲に合わせて上下を空けません．点灯範囲を変更した場合は，atlasと実機の両方で確認します．

## atlasによる確認

```powershell
python -X utf8 tools/render_bitmap_atlas.py `
  --source App/font.c `
  --source App/japanese_font.c `
  --source App/bitmaps.c `
  --out tmp/uv-k1-bitmap-atlas-annotated
```

`bitmap_atlas_inventory.json`には，フォント配列について次の情報が含まれます．

- コードポイント，ソース上の注釈，占有／空き状態
- グリフの元バイト列（重複比較用）
- 指定初期化子で省略された空スロット

`bitmap_atlas.svg`は形状の目視確認用です．ビットマップ配列は`BITMAP_*`のシンボル名と元配列のバイト列を記録し，文字コードとは別の資産として扱います．

## 追加時の規則

1. まず両機種のatlas inventoryでコードの占有状態とバイト列を確認する．
2. 既存グリフと同じ意味のコードを新設しない．共通化する場合はK5/K1双方に同じコード注釈を付ける．
3. 共通の新規文字は，現時点では`0x9A`–`0xA0`から必要数だけ割り当てる．追加前に再度inventoryを生成する．
4. C配列の行または指定初期化子に，コードと意味を示す短いコメントを付ける．
5. atlas，ソースコメント，表示文字列の対応を確認してから，実機で使う文字を追加する．

inventory確認後，起動画面の「受信専用」に必要な大グリフとして`0x98=専`，`0x99=用`を公開フォントから変換して実装しました．K1では`App/japanese_font.c`の指定初期化子，K5では`font.c`の連続配列に同じ14-byte字形を保持しています．小フォントには追加せず，現時点では大フォント専用です．次に追加する文字は，空き領域`0x9A`–`0xA0`と再生成したinventoryを確認してから割り当てます．

今回の`font-glyph-0x98.json`／`font-glyph-0x99.json`を含む個別JSONは確認用の受け渡し形式です．継続編集には`tools/font_source_json.py extract`で完全スナップショットを作成し，各要素の`base_bytes_hex`を基準にしてください．適用は一時Cファイルへ行い，atlasと差分を確認してからソースへ反映します．特大字形は公開フォントの線構造を手掛かりに独立再構成した10×16セルです．出所と変換規則は[FONT_SOURCES.ja.md](FONT_SOURCES.ja.md)に記録しています．

# LCDエミュレーター

この検査経路は、Pythonで画面レイアウトを再実装するモックではない。`JpLcdDebug`ファームウェアが実際のC描画処理を実行し、ST7565へ渡す物理フレームバッファをプログラミングケーブル経由でPCへ送る。`tools/lcd_emulator.py`の役割は、要求の送信、フレームの検証、PNGへの変換に限定する。

## 構成

```text
PC ──既存UARTコマンド──> LCDデバッグファーム
PC <── LCDF + 1024 bytes ── LCDデバッグファーム
                              │
                              └─ UI_DisplayMenu / UI_DisplayMain 等の実装
```

LCDの物理フレームは、次の1024 bytesで構成する。

- `gStatusLine`: 128 bytes
- `gFrameBuffer`: 7ページ × 128 bytes
- 各ページの各ビットは、ST7565の縦8ドットに対応する

したがって、PC側は文字幅や座標を推測せず、受信したページ順データをそのまま画像へ展開する。

## ビルド

リポジトリのルートで実行する。

```powershell
cmake --preset JpLcdDebug
cmake --build --preset JpLcdDebug --parallel 2
```

生成物は`build/JpLcdDebug/wrx-jp-lcd-debug.bin`である。デバッグ版はハードウェアUARTを使用し、USB/VCPは有効にしない。通常の無線初期化とアプリケーションループへ進まず、起動後は画面生成とフレーム応答を待つ。

## 標準テストパターン

`--all`は、画面監査で使う標準パターンをこの順番で取得する。各イベントは
ファームウェア側の実装済み描画関数を直接呼び出す。イベント番号は
`App/app/lcd_debug.h`と`tools/lcd_emulator.py`で一致させる。

| イベント群 | 確認対象 |
| --- | --- |
| `menu`, `menu-help` | メニュー項目、左右切替、補足説明 |
| `menu-cat-*` | K1で実際に表示されるカテゴリのアイコン、カテゴリ名、件数、ページ表示 |
| `menu-item-*` | 値の境界、長いラベル、確認表示、CSSスキャン表示、フォント設定、操作選択 |
| `preset-bank` | 受信プリセットバンクのタイトル、範囲、変調方式、操作説明 |
| `scan-*` | リスト名、メモリー／デュアル／範囲スキャンの進捗、優先表示 |
| `warning-*` | 受信専用、FM専用、受信拡張、プリセット、スキャン結果の警告 |
| `receive-*` | 周波数、チャンネル番号、名前、名前＋周波数、単一／デュアルVFO、主画面フォント、スキャンリスト所属表示 |
| `receive-jp-*` | 固定した日本語チャンネル名による16×16・14×14・8×8・名前＋周波数・デュアル表示 |
| `receive-audio-*` | 無音、ゲート直下、音声形状、強信号、交互、インパルス、階段、飽和、単一／デュアルVFOの音声スコープ |
| `receive-am`／`receive-usb` | AM／USBの変調表示と受信画面の余白 |
| `receive-ctcss*`／`receive-dcs*` | CTCSS／DCSの正逆表示とコード・帯域幅・スケルチ表示 |
| `receive-bandwidth-*`／`receive-monitor` | W+／W／N／N-、MONIの表示と右端の欠け |
| `receive-dual-b` | デュアルウォッチのB側選択表示 |
| `main-*`／`status-*` | 低電池、キーロック、DTMF入力、範囲表示、通常／走査／デュアルのステータス領域 |

進捗画面の番号や範囲は、再現性のある画面を作るためデバッグ経路が固定値を与える。通常の`receive-*`は受信画面の周波数・チャンネルを固定し、チャンネル名は外部Flashの名前テーブルを読む。`receive-jp-*`は外部Flashの状態に左右されないよう、デバッグ専用のメモリー上の名前（`東京空港`、`羽田AIR`）を実装済みの描画経路へ渡す。名前が未登録の場合も、実装どおりのASCIIフォールバックを表示する。

`receive-audio-*`はBK4829の振幅エンベロープ読出しを模した値だけをデバッグ版へ注入し、音声スコープの履歴・床値・ノイズゲート・循環バッファ・中央仕切り行を実装どおりに描画する。注入機能は`ENABLE_LCD_DEBUG`時だけ存在し、通常版のRF入力経路は変更しない。音声内容そのもの、スケルチ開閉、受信音、実際のRFスキャンは再現しないため、[実機テスト計画](HARDWARE_TEST_PLAN.ja.md)のRF項目で確認する。

## 実機から取得する

たとえば，デバイスマネージャーでケーブルが`COMx`として認識されている場合は次のようにします．

```powershell
python tools/lcd_emulator.py --port COMx --event menu --out tmp/lcd-menu.png
python tools/lcd_emulator.py --port COMx --all --out tmp/lcd-debug
```

`--all`では各イベントのPNGと、一覧確認用の`contact-sheet.png`を出力する。配色は`--lcd classic`（既定）または`--lcd orange`、拡大率は`--scale 4`（既定）で変更できる。

RX-onlyでは送信関連のタイマー項目がメニューへ登録されないため、`menu-cat-timers`は標準イベントに含めない。`receive-scanlist-present`は、チャンネルを名前付きスキャンリストへ登録した状態を確認するパターンである。通常の`receive-*`パターンは未所属（`OFF`）を確認する。

COMポートが自動選択されることはない。誤ったポートへの書き込みや読出しを避けるため、必ず`--port`で対象を指定する。

## 取得済みフレームの変換

PC側で保存した1024-byteの物理フレームは、通信なしでPNGへ変換できる。

```powershell
python tools/lcd_emulator.py --raw frame.bin --out tmp/lcd-raw.png
```

## 通信形式

要求は、既存のUARTコマンドフレーム（38400 baud、XOR難読化、XMODEM CRC）を使用する。デバッグ専用のコマンドIDは`0x06F0`で、本文はイベント番号と予約バイトの2 bytesである。

応答は既存の短い応答形式ではなく、次の12-byteヘッダーと1024-byteフレームを連結する。

| オフセット | 長さ | 内容 |
| ---: | ---: | --- |
| 0 | 4 | ASCII `LCDF` |
| 4 | 1 | プロトコルバージョン |
| 5 | 1 | イベント番号 |
| 6 | 1 | ステータス（`0`は成功） |
| 7 | 1 | フラグ（現在は`0`） |
| 8 | 2 | フレーム長（little-endian、1024） |
| 10 | 2 | フレームのXMODEM CRC（little-endian） |
| 12 | 1024 | `gStatusLine`と`gFrameBuffer`の連結データ |

起動時に送られる通常のバージョン文字列は、PC側が`LCDF`を探索して読み飛ばす。フレーム長とCRCが一致しない場合は画像を生成しない。

## 検査範囲と限界

- 画面の座標、文字の重なり、右端の欠け、上下位置、単一／デュアルVFOの切替を、ファームウェアの描画結果で確認できる。
- PC側の画像化はST7565のページ・ビット配置だけを扱う。UIの描画規則を複製していない。
- デバッグ版はRF初期化、無線スキャン、送信処理を実行しない。RX-onlyの安全境界を維持した画面検査用ビルドである。
- `--all`はイベントごとの描画応答を連続取得するが、ファームウェアの全操作体系を自動操作するものではない。
- PCからのキーイベント注入は現行版では提供しない。`--all`のイベント単位で、実装済みの画面状態を確認する。
- ビルド、通信、PNG生成の成功は、LCD実機のコントラスト、ケーブル接続、フラッシュ後の実機動作を保証しない。実機で取得したフレームと、静的テスト・ビルド結果は分けて扱う。

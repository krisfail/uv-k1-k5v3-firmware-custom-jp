# 上流差分コードレビュー

## レビュー範囲

2026-08-23時点で，`upstream/main`（`3bd3ebba2ceb553edc88c3f087ce0c7f420433b2`）とこのリポジトリの`HEAD`（`7dc5c0a2a12f3db2618f068c79c96784eccefd4e`）を比較した．対象は，上流コードに対してこのフォーク側が加えた変更と，その変更が作る挙動だけである．上流から変更なく取り込んだコードの品質は，このレビューでは評価していない．

受信専用境界，日本語表示，受信機向け設定，フォーク固有のビルド定義を中心に確認した．ホストテストの成功は，LCD表示，無線動作，実機書き込みの保証を意味しない．

## 指摘事項

### [P1] W/Nメニューの4段階表示と内部値の対応が一致しない（対応済み）

対象：`App/app/menu.c`の`MENU_W_N`処理，`App/app/action.c`の`ACTION_Wn`処理．

レビュー時点では，メニュー表示の4項目に対してRX-only分岐の選択処理はインデックス2だけを`N-`として扱い，それ以外を`WIDE`にしていた．そのため，表示上の`W+`と`N-`が正しい内部帯域値にならなかった．現在値の読み戻しも`WIDE_PLUS`を考慮せず，4項目を正しく復元できなかった．

さらに，レビュー時点の`ACTION_Wn`は`W`→`N`→`N-`→`W`の3段階を循環し，`W+`を通らなかった．`App/radio.h`には4段階を相互変換するヘルパーがあるため，メニューとアクションが同じ変換経路を使う必要があった．

影響は，利用者が選択した帯域幅と実際にBK4829へ設定されるフィルタが一致しないことだった．特に25 kHz相当の`W+`と6.25 kHz相当の`N-`は，レビュー時点のK1メニューから正しく設定できなかった．

対応として，`gSubMenu_W_N`を4項目へ拡張し，選択・読み戻し・アクション循環を`RADIO_BandwidthFromMenuIndex()`，`RADIO_BandwidthToMenuIndex()`，`RADIO_NextBandwidth()`へ統一した．周波数画面の表示も同じインデックス変換を使う．

### [P2] 帯域幅メニューの往復検証がホストテストにない（対応済み）

4項目の表示，変換ヘルパーの使用，アクション循環を`test_k1_receive_bandwidth_has_four_modes_and_preserves_step_choices`で検証する．実機では，`W+`，`W`，`N`，`N-`の選択・保存・再表示を個別に確認する必要がある．

## レビューで問題を確認しなかった範囲

- 上流から変更なく取り込まれた機能は，レビュー対象外とした．
- 受信専用ビルド定義，PTTのモニター割り当て，予期しないTX要求の拒否経路について，今回確認したフォーク側の境界に追加の指摘はない．ただし，実機でTXが発生しないことは別途確認が必要である．
- 日本語フォントの字形品質やLCD上の視認性は，コード差分だけでは判定できないため，この文書のコードレビューの結論には含めない．
